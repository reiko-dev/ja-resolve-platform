SYMPTOM (before this correction)
--------------------------------
`GET /api/tow/partner/opportunities` returned items of exactly
`{request, route_quote, proposed_price}` while the canonical entrypoint
`docs/tow/tow-api-contract.openapi.yaml` declared
`TowOpportunity.required =
 [request, active_tow_vehicle, route_quote, proposed_price, compatibility,
  opportunity_expires_at]`.
The runtime was therefore NOT conformant to its own frozen contract, and
`tests/tow/mvp03/towPartnerOpportunities.test.js` had LOCKED the reduced shape.

The reduced shape was never a contract decision: it was an implementation gap.
No schema was edited to excuse it; the runtime was made truthful instead.

[4] WHY THE OLD TEST DID NOT CATCH THIS (root cause, disclosed)
================================================================================
The pre-existing consumer smoke test generated a fixture through the contract's
own `generateFixture` helper, and arrays generate as `[]`:
    {"success":true,"data":{"items":[],"meta":{"page":1,"limit":2}}}
so `data.items[0]` never existed and the ITEM schema was never exercised.
That is exactly the hole this new live-endpoint test closes: it asserts a REAL
non-empty item produced by the REAL endpoint.

[5] SCOPE OF THE FIX
================================================================================
- `active_tow_vehicle` is the ACTUAL vehicle used for eligibility and quoting
  (`matching-service.js` carries the `vehicle` it evaluated), projected to
  `TowVehicleSummary` (10 fields, no tariff) by reusing the new
  `serializeVehicleSummary`, which `serializeVehicle` also composes — so the
  summary and the full vehicle cannot drift.

  eligibility.js -> matching.js -> matching-service.js). No second policy, no
  recomputation in the HTTP layer: the serializer only narrows the object to the

  scheduler, no search timeout and no proposal lifecycle, so no truthful instant
  exists to emit.
- The geodesic (Haversine) distance used for radius filtering is still NOT
  serialized. The only distance on the wire remains the authoritative
  Google Routes `route_quote.total_distance_meters`.
